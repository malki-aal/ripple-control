## Databricks — graph data preparation and validation
`databricks/ripple_graph_build.py` (Databricks notebook source format; also runs locally on PySpark).

- Ingests the 16 extracts, builds `entity_keys`, `graph_nodes`, `graph_edges` (namespaced keys, source table + record key,
  derived Lot→ProductionOrder edge) with the same rules as `ripple/graph.py`.
- Validates unique keys, edge endpoints, orphaned BOM / plant-model / shipment / lot / order / vehicle links.
- Impact-path checks for one delay (SH-0182 → 2027-03-18) and one hold (LOT-0191).
- Parity: compares canonical node and edge keys + provenance with `runs/run1/export/graph_*.csv` for the same snapshot.
- Publishes with Delta `MERGE` on `(snapshot_id, key)`; locally writes CSV stand-ins.

Local rehearsal result (2026-11-07, snapshot `9b1551f5b55378ef`): validation all OK; parity **MATCH**
(17,029 nodes, 28,201 edges, 0 differences, 0 provenance mismatches); impact checks equal the agents' E-12 / E-15 results.

## Snowflake — audit reporting
`snowflake/load.py`, `snowflake/schema.sql` (generated by `load.py --print-ddl`).

- Tables `AUDIT_EVENTS (run_id, event_id)`, `AUDIT_INCIDENTS (run_id, event_id, incident_id)`,
  `AUDIT_ACTIONS (run_id, event_id, action_seq)` + transient `STG_*` staging tables.
- Views `V_RUN_SUMMARY`, `V_EVENT_OUTCOMES`, `V_FAILED_CALLS`, `V_ESCALATIONS`, `V_ACTION_POLICY`.
- Load: dedupe input keys → truncate staging → bound `executemany` → `MERGE` → verify count = distinct keys = exported.
- Uses both `event_traces.jsonl` (noise events with zero calls, policy and rationale) and the official `action_log.jsonl`
  (each action carries `server_logged` / `server_ok`; `failure_class` separates `server_rejection` from `client_timeout_unknown`).
- Published fields only: no event text, messages or raw args; customer ids, customer order ids and VINs are HMAC pseudonyms.

```
python integrations/snowflake/load.py --export runs/run1/export --dry-run --repeat 3   # offline SQLite rehearsal
python integrations/snowflake/load.py --export runs/run1/export                        # needs SNOWFLAKE_* env (see .env.example)
```
Local rehearsal (2026-11-07): three publishes of the same run → 15 / 16 / 900 rows each time, no duplicates.
**Published to a real Snowflake trial (2026-11-07):** run2 published twice gave 15 / 16 / 900 rows with 900 distinct action keys, and all 5 views return results. Login is key-pair (`SNOWFLAKE_AUTHENTICATOR=SNOWFLAKE_JWT`, `SNOWFLAKE_PRIVATE_KEY_FILE`). The public key is registered with `ALTER USER <login> SET RSA_PUBLIC_KEY='...'`.


## MongoDB Atlas: precedent search ("similar past incidents")
`mongodb/precedents.py` gives the human reviewer the closest earlier incidents and what was done about them.
- Each incident gets a structured description built from trace facts: type, supplier/part/plant names, impact size,
  decision and rule. No raw event text and no customer ids.
- The description is embedded with Gemini `gemini-embedding-2` (768 dimensions) and stored in `ripple.incidents`
  (`_id = run_id:incident_id`).
- Queried with Atlas `$vectorSearch` (index `incident_vec`, cosine, filtered to the run, other events only). Same-type
  precedents come first; another type is shown only at a score of 0.96 or above. `why_similar` is computed in code
  from shared attributes.
- Output: `<run>/similar_incidents.json` (contract in `ORLANDO_UI_BUILD_BRIEF.md` section 6), copied to `submission/`.

```
python integrations/mongodb/precedents.py --run runs/run2 --also submission    # Atlas (MONGODB_URI in .env)
python integrations/mongodb/precedents.py --run runs/run2 --backend local      # same embeddings, local cosine
```
Run on Atlas M0 (2026-11-07): 16 incidents stored and the vector index built. Neighbours are identical to the
local-cosine check for 14/16 incidents; the other 2 differ only in the order of tied noise events (score 1.0).
